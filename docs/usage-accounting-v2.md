# Observed usage accounting v2

The Analytics dashboard and `/api/analytics/overview` now report validated token observations, exact API estimates, and explicit unknown costs. This is observation only: no request admission, spending ceiling, cron attribution, model switching, or invoice reconciliation is implemented.

## API compatibility

`costs.schemaVersion` is `2`. `costs.currentMonth` is now a summary object rather than a number. Daily rows and model breakdowns carry the same summary fields: `cost` (nullable USD), `cost_status` (`estimated`, `billed`, `unknown`), `estimated_usd`, `billed_usd`, `unknown_entries`, `entries`, and `tokens`. `byModel` daily series contains nullable model values plus `cost_status` and `unknown_entries`. Consumers must check the version and status and must never coerce null to zero. Update mobile/third-party consumers before deploying this API; no backward-compatible scalar is provided because it could misrepresent unknown amounts.

`estimated_usd` and `billed_usd` are subtotals for observed entries of that status. An empty subtotal is null. Unknown entries, incomplete/stale source coverage, accounting issues, or a mix of billed and estimated entries make the combined `cost` null. No current adapter emits `billed`; it is reserved for future verified reconciliation. These amounts cover token costs from discovered sources only, excluding KB, tool, media, and other provider fees.

Claude transcripts can also contain an observed `message.costUSD` or top-level `costUSD`. The former parser passed that amount through as cost; the initial v2 revision dropped it. V2 now preserves it separately as `reported_cost_usd` / `reported_cost_micros`, with `reported_cost_source` naming the field and `source_file` naming its transcript. It does not establish a bill or supply missing pricing/billing evidence. Month, daily and model summaries expose `reported_usd` and `reported_entries`, including zero; absent amounts remain null. The dashboard labels these as transcript-reported subtotals. They may overlap independently calculated estimates and must never be added to estimated or billed subtotals.

Reported amounts must be finite nonnegative numbers that fit safe integer microdollars (rounded to six decimal USD places); strings, null, negative values and overflow raise `invalid_reported_cost`. Streaming/replayed observations are deduplicated by the same message/request identity as tokens. Only costs attached to the maximal token snapshot qualify; an earlier partial amount is never carried onto a larger snapshot. Duplicate maximal snapshots may fill an omitted amount, but disagreeing amounts or disagreeing top-level/nested fields raise `conflicting_reported_cost` and leave the reported amount unknown while retaining validated tokens. A newly observed amount changes the cache identity so an older ignored-field payload cannot shadow it. Existing payloads without the fields read as unknown reported cost. Source-reported historical amounts do not require a current price-table match.

## Identity and token semantics

Codex `tokenUsage.total` is session cumulative. The first sample establishes a baseline; a nonzero baseline is unallocated and raises an issue. Later observations yield deltas across turn boundaries. Identical counter snapshots are treated as replays, even at later timestamps. A new, lower counter vector quarantines the whole session. A reset identical to a prior vector is indistinguishable from a replay in this source; exact request accounting requires the later request adapter. Overlapping sessions keep separate baselines. Cached input and cache writes are subtracted from total input to make disjoint categories.

Claude streaming blocks and duplicate transcript files are grouped by session/message/request identity; monotone usage observations produce one maximal record. Missing request IDs are joined through known message aliases. Conflicting request aliases, metadata, or incomparable counters are rejected with issues. Claude input, cache reads, and cache writes are disjoint. Cache writes with an unknown 5-minute/1-hour breakdown retain tokens but cannot be priced.

Configured Codex model identity remains useful diagnostic context, but pricing requires `model_source: observed` and `observed_model`. Legacy model fields alone do not establish that evidence. API billing, provider, tier, region, context band (when price-dependent), and known cache semantics must also be supplied. The present writer marks billing and cache writes unknown, so its tokens usually have unknown cash cost. Subscription use does not become an API charge. Unsupported counter scopes and malformed/future telemetry raise issues.

## Price snapshot

`2026-09-10.v1` describes observed standard/global API token prices for exact model identifiers. No fuzzy aliases or default Sonnet rate remain. Astra requires an explicit short/long context band; the session cumulative count is never used to infer a request's context band. Older observations are not assigned this snapshot. Event IDs omit the rate version, and SQLite inserts ignore existing identities, preserving the first price snapshot for each event. Add a new version for future prices; do not silently edit a published snapshot or backprice older observations.

Sources checked September 10, 2026: [OpenAI pricing](https://developers.openai.com/api/docs/pricing), [GPT-5-Codex](https://developers.openai.com/api/docs/models/gpt-5-codex), and [Claude pricing](https://platform.claude.com/docs/en/about-claude/pricing). Exact rate rows live in `dashboard/src/lib/usage-pricing.ts`. Rates are estimates, not evidence of this installation's billing conditions or invoice amounts.

The Claude cache-rate formulas in that table are list-price observations (read default 0.1x input, 5-minute write 1.25x, 1-hour write 2x), not measurements of this installation. Listed model identifiers need not occur in local transcripts. In particular, an unlisted `claude-opus-5` stays unpriced even when its transcript contains a separately preserved reported amount; no alias or invented price fills that gap. `calculateCost` remains a compatibility/test helper for explicit hypothetical estimates; normalization calls `resolvePrice` and `priceMicros` directly.

## Sources and non-destructive cache migration

The schema additively creates `usage_entries_v2` and `usage_health_v2`. It retains the old `cost_entries` table and reports its excluded row count. Source files are never rewritten. No legacy guessed total is included in corrected totals.

A sync transaction deactivates prior cache rows and activates the validated rows available in the current source scan. Growing Claude messages supersede the earlier active snapshot; old payloads remain inactive for audit. Missing, unreadable, changed, or removed sources can shrink the active view. That view is not a complete historical ledger. The inactive rows are not blindly carried into totals because doing so could double count a replaced request or preserve a quarantined session. Keep source archives and the database when historical audit is needed; rebuilding an empty cache with a later price table does not reproduce earlier snapshots automatically.

`health` includes observation time, six-hour staleness threshold, accounting issues, excluded legacy rows, and instruments with `fresh`, `stale`, `missing`, `unreadable`, `empty`, `invalid`, or `unsupported` status. A partial Claude file failure prevents a fresh aggregate instrument. Staleness describes age, not proof that a writer broke. Historical logs from a different runtime remain readable history; the configured current runtime determines the expected instrument. No sources is unknown, never zero usage. Analytics refreshes at most every five minutes; stored health becomes unknown after six hours without a successful scan.

Scope audit: `getCostIntelligence` in `data/reports.ts` is a separate legacy snapshot helper with no current dashboard/app callers. Its costs now carry unknown status and null totals; raw per-agent historical amounts are named `legacyReportedCostUsd`. It is not this corrected cache or an invoice source. Plan usage panels remain percentage observations, not cash debits. The usage status card remains visible alongside both subscription panels.
